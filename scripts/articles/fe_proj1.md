# 需求分析与用户故事编写

在软件开发的世界里，代码只是冰山一角。真正决定项目成败的，往往是在写下第一行代码之前的需求分析工作。一个功能再强大的系统，如果不能解决用户的真实问题，那就是一堆昂贵的废品。本文将深入探讨如何从混沌的需求中提炼出清晰的产品定义，以及如何用结构化的方式描述和管理需求。

## 需求收集的三种路径

### 用户访谈：听见真实的声音

用户访谈是最直接的需求收集方式，但也是最容易踩坑的方式。很多产品经理把访谈做成了"确认式提问"——"你觉得这个功能好不好？"这种问题几乎得不到有价值的信息。

有效的用户访谈应该遵循以下原则：

**开放式提问**：不要预设答案。把"你觉得搜索功能够用吗？"换成"你平时找文章的时候是怎么操作的？"

**关注行为而非态度**：用户说的和做的往往不一致。与其问"你会不会用收藏功能"，不如问"你上次收藏一篇文章是什么时候，当时为什么想收藏？"

**追问场景**：每个需求背后都有一个具体的使用场景。当用户说"我想要一个标签功能"时，继续追问"你在什么情况下会想到用标签？现在没有标签你是怎么解决的？"

访谈记录应该包含三个维度：

```markdown
## 访谈记录模板

### 基本信息
- 用户角色：技术博主
- 访谈时间：2024-01-15
- 访谈时长：45分钟

### 关键发现
1. 痛点：文章多了之后难以分类管理
2. 现有解决方案：用文件夹手动整理，效率低
3. 期望：希望能按技术栈自动归类

### 原始引用
> "我写了200多篇文章，每次找某个知识点的文章都要翻半天，
> 虽然有分类功能但不够灵活，一篇文章只能属于一个分类。"
```

### 竞品分析：站在巨人的肩膀上

竞品分析不是简单地罗列功能列表，而是要理解竞品背后的设计决策。

**直接竞品**：CSDN、博客园、掘金、思否等技术博客平台

**分析维度**：

| 维度 | CSDN | 博客园 | 掘金 | 码上记（目标） |
|------|------|--------|------|---------------|
| 内容管理 | 文件夹分类 | 标签+分类 | 专栏+标签 | 多维分类+智能标签 |
| 编辑器体验 | Markdown基础 | 富文本为主 | Markdown增强 | 实时预览+快捷键 |
| SEO支持 | 较好 | 一般 | 较好 | 需重点优化 |
| 数据统计 | 基础 | 基础 | 详细 | 详细+自定义 |

竞品分析的关键是找到**差异化机会**。不要试图在所有维度上超越竞品，而是找到一两个核心差异点深耕。

### 数据驱动：让数据说话

如果有现成的系统，数据分析是最客观的需求来源：

```sql
-- 用户行为分析示例
-- 找出用户最常访问但跳出率高的页面
SELECT 
    page_path,
    COUNT(*) as visit_count,
    AVG(session_duration) as avg_duration,
    SUM(CASE WHEN bounce = 1 THEN 1 ELSE 0 END) / COUNT(*) as bounce_rate
FROM user_behavior_logs
WHERE created_at >= DATE_SUB(NOW(), INTERVAL 30 DAY)
GROUP BY page_path
HAVING visit_count > 100
ORDER BY bounce_rate DESC
LIMIT 20;
```

数据能帮你发现：
- 用户实际使用路径与预期的偏差
- 功能使用率的长尾分布
- 性能瓶颈所在

## 用户故事：用业务语言描述需求

### 标准格式

用户故事是敏捷开发中最常用的需求描述方式，它的核心格式是：

```
As a [角色]
I want [功能]
So that [价值]
```

这个格式看似简单，但写好并不容易。关键是**So that**部分——它描述的是业务价值，而不是技术实现。

**反面示例**：

```
As a user
I want a Redis cache layer
So that the database queries are faster
```

这是一个技术方案，不是用户故事。用户不关心你用什么缓存，他们只关心体验。

**正面示例**：

```
As a blog reader
I want articles to load within 2 seconds
So that I can quickly find the information I need without waiting
```

### 验收标准：Given/When/Then

用户故事描述了"做什么"，验收标准则定义了"怎么才算做好"。推荐使用Gherkin语法：

```gherkin
Feature: 文章搜索功能

  Scenario: 按关键词搜索文章
    Given 用户在博客首页
    And 存在标题包含"Spring Boot"的文章
    When 用户在搜索框输入"Spring Boot"并点击搜索
    Then 搜索结果页面应该显示匹配的文章列表
    And 每篇文章应该显示标题、摘要和匹配高亮

  Scenario: 搜索无结果
    Given 用户在博客首页
    When 用户在搜索框输入一个不存在的关键词
    Then 页面应该显示"未找到相关文章"的提示
    And 提供推荐文章列表

  Scenario: 搜索性能要求
    Given 数据库中有10000篇文章
    When 用户执行任意关键词搜索
    Then 搜索结果应该在500毫秒内返回
```

这种格式有几个好处：
- **可测试**：每个场景都可以直接转化为自动化测试
- **无歧义**：业务人员和开发人员都能理解
- **完整**：覆盖了正常流程、异常流程和非功能需求

### 验收标准的层次

一个用户故事可能有多层验收标准：

```gherkin
# 功能验收
Given 用户已登录
When 用户点击"发布文章"
Then 文章应该出现在公开列表中

# 边界条件
Given 用户输入的文章标题超过200个字符
When 用户点击"发布"
Then 应该显示标题过长的错误提示

# 非功能需求
Given 文章包含10张图片
When 用户点击"发布"
Then 上传和发布过程应该在30秒内完成
```

## 需求优先级排序

### MoSCoW方法

MoSCoW将需求分为四个优先级：

- **Must Have**：没有这个功能，产品无法上线。比如博客系统的文章发布功能。
- **Should Have**：重要但不是阻塞性的。比如文章的草稿自动保存。
- **Could Have**：锦上添花的功能。比如文章的阅读进度条。
- **Won't Have**：明确不做，但记录下来以备将来考虑。

使用MoSCoW时要遵守一个约束：Must Have的比例不应该超过60%。如果所有需求都是Must Have，说明优先级划分没有意义。

### 价值-复杂度矩阵

更直观的方式是用二维矩阵来排序：

```
价值高  │ Quick Wins    │ Big Bets      │
        │ (优先做)       │ (重点规划)     │
        │───────────────────────────────│
价值低  │ Fill Ins      │ Money Pit     │
        │ (有空再做)     │ (避免投入)     │
        └───────────────────────────────┘
           复杂度低        复杂度高
```

实际操作中，可以给每个需求打分：

```markdown
| 需求 | 业务价值(1-5) | 技术复杂度(1-5) | 优先级 |
|------|--------------|----------------|--------|
| 文章Markdown编辑器 | 5 | 2 | Quick Win |
| 多人协作编辑 | 3 | 5 | Big Bet |
| 文章定时发布 | 2 | 1 | Fill In |
| 实时协同编辑 | 2 | 5 | Money Pit |
```

### Kano模型

Kano模型从用户满意度的角度分析需求：

- **基本型需求**：做了用户觉得理所当然，不做用户会很不满。比如登录功能。
- **期望型需求**：做得越好用户越满意。比如搜索速度。
- **兴奋型需求**：做了用户会惊喜，不做用户也不会期待。比如智能推荐。

对于技术博客系统，基本型需求是文章CRUD、用户认证；期望型需求是搜索、分类；兴奋型需求可能是AI摘要、智能标签。

## PRD文档结构

一份完整的PRD（Product Requirements Document）应该包含以下部分：

```markdown
# 产品需求文档

## 1. 文档信息
- 版本：v1.0
- 作者：产品经理
- 日期：2024-01-15
- 状态：评审中

## 2. 背景与目标
### 2.1 业务背景
### 2.2 产品目标
### 2.3 成功指标

## 3. 用户画像
### 3.1 目标用户
### 3.2 用户场景

## 4. 功能需求
### 4.1 功能列表
### 4.2 功能详情
#### 4.2.1 功能名称
- 需求描述
- 用户故事
- 验收标准
- 交互说明
- 异常处理

## 5. 非功能需求
### 5.1 性能要求
### 5.2 安全要求
### 5.3 兼容性要求

## 6. 数据需求
### 6.1 数据埋点
### 6.2 数据字典

## 7. 风险与依赖
### 7.1 技术风险
### 7.2 外部依赖

## 8. 排期与里程碑
```

### 功能详情示例

以"文章分类管理"功能为例：

```markdown
#### 4.2.3 文章分类管理

**需求描述**
支持作者对自己的文章进行多级分类管理，每个作者拥有独立的分类体系。

**用户故事**
As a blog author
I want to organize my articles into categories
So that readers can easily find related content

**验收标准**
Given 作者已登录
When 作者进入分类管理页面
Then 应该显示该作者的所有分类及文章数量

Given 作者创建一个新分类
When 分类名称与已有分类重复
Then 应该提示"分类已存在"

Given 分类下已有文章
When 作者删除该分类
Then 应该提示"该分类下有N篇文章，请先移除"
And 不允许直接删除

**交互说明**
- 分类支持拖拽排序
- 支持三级分类深度
- 分类slug自动根据名称生成，可手动修改

**异常处理**
- 分类名称包含特殊字符：过滤HTML标签，保留中文、英文、数字
- 分类数量超过限制：提示上限，建议合并
```

## 需求评审与变更管理

### 评审清单

需求评审会前，确保以下问题已有答案：

- [ ] 需求的业务价值是否明确？
- [ ] 验收标准是否可测试？
- [ ] 是否考虑了边界条件和异常情况？
- [ ] 是否有技术可行性评估？
- [ ] 是否有明确的优先级？
- [ ] 是否考虑了数据迁移和兼容性？

### 变更控制

需求变更是不可避免的，但需要有流程控制：

```markdown
## 需求变更申请

### 变更内容
原文章标题限制50个字符，变更为200个字符

### 变更原因
用户反馈技术文章标题通常较长，50个字符不够用

### 影响评估
- 前端：修改表单校验规则，数据库字段长度调整
- 后端：数据库DDL变更，需要Flyway迁移
- 测试：更新相关测试用例
- 预计工时：2人天

### 审批
- [ ] 产品负责人
- [ ] 技术负责人
- [ ] 测试负责人
```

需求分析是一项需要不断练习的技能。好的需求文档不是写得越长越好，而是让团队成员都能准确理解"做什么"和"为什么做"。当你发现自己写的需求文档在评审会上几乎没有问题被提出，那才是真正的好文档。
